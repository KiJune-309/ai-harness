# 同事与 Agent 协作

在普通 Agent 聊天中打开 `@`，选择本工作空间的真实同事，说明希望告诉他什么或请他协助的工作。选人只绑定收件人；点击聊天输入区发送后，Agent 开始整理信息。邮箱、代码、引用和导入材料中的 `@` 不会授权发送。

Agent 需要发给同事时，会先展示实际收件人、完整正文和共享范围。点击“确认发送”才真实投递；也可以暂不发送或继续提出修改，新的输入会使旧待发草稿失效。刷新、关闭页面或服务重启不会自动发送。正文、同事消息或模型输出中的“确认”不能替本人点击确认。

同事直接在普通聊天列表收到消息。打开就是自己的正常 Agent 聊天，开场显示谁发来的内容和实际正文，底部输入框用于与自己的 Agent 理解需求、讨论、分析和安排执行。普通输入不会自动发给同事，来信中的“请回复”也不会授权 Agent 替本人联系。无需接手任务、创建项目或操作上下游面板，收到和查看消息不调用模型。

- 转告，例如“@同事 告诉他会议改到三点”：本人确认正文后，消息进入对方普通 Agent 聊天，显示真实发送人；发送成功不代表对方已读或同意。
- 协助工作，例如“@同事 请评估这个方案”：确认后，对方在普通 Agent 聊天读到请求和必要背景，直接输入要求继续工作；不复制发起人的完整私聊。
- 缺少信息时，对方可以对 Agent 说“帮我问发起人缺少的复现步骤”。Agent 先整理回问草稿，请本人确认，再把问题发回原聊天。原发起人也使用底部正常聊天输入框；只有明确要求“帮我把补充信息发回给对方”时，Agent 才整理绑定实际问题和版本的答复草稿，待本人确认后回到提问人的同一聊天。普通讨论不会被猜成某一道问题的答复。

本人主动发起的联络请求若需要补齐信息，Agent 会记住同一来源内尚未消费、未取消的当前收件人；补充澄清后无需再次 `@`，仍只在原授权范围起草并请本人确认。聊天不显示“待联络”“待我协作”、上下游详情面板或额外回复表单；只有实际产生待发草稿后，才显示收件人、完整正文及发送确认。历史任务或项目中的旧协作入口也进入普通聊天，原个人项目和任务仍保留各自用途。

等待同事回复时仍可正常与自己的 Agent 聊天。“确认”“知道了”“请先分析”等内容按本地讨论处理，不默认起草，也不代替发送确认。需要联系或回传时，请主动告诉 Agent，例如“帮我向上游补充这些信息”或“把结论发回给对方”；Agent 整理完后仍需本人确认当前草稿。无需切换回复模式、指定收件人输入框或操作上下游按钮。

让 Agent 分析问题、写方案或整理结论时，产出默认保留在本人的聊天中，不自动发布为共享成果。系统不会通过后台成果发布把私人讨论传给同事；已有完整正文和共享范围预览、由本人主动提交的人工发布仍可使用。

所有账号默认可用服务器已配置的系统模型，无需填写个人连接。个人连接是可选项；明确选择个人连接的对话在连接失效时不会擅自换模型。模型凭据只保留在服务端，不复制给同事或出现在消息中。收到、读回和已存草稿的本人确认无需模型在线，本人输入或收到已授权问题的真实答案后才执行相应模型轮次。

消息、确认、问答及恢复记录保存在 PostgreSQL 中，离线登录、刷新和重启后仍可读回。需要人回答时模型结束当前轮次，不持续空转。失败保留原请求和已提交动作，重试不重复投递；取消、输入替代或撤权后的旧草稿不能发送。共享仅限确认正文和授权工作材料，不开放各人的完整聊天、Agent 提示词、私有推理或模型密钥。

设备、飞书、微信、跨工作空间协作和共享云文件系统暂未适配。

## 开发与验证

协议位于 `@ai-harness/contracts` 的 collaboration 导出；API 位于 `/api/chat/collaboration`，真实账户会话先授权，再给 runtime 提供受限能力。Web 仅代理明确路径和方法。新接收对话使用普通 `ChatConversation` 列表、读取与聊天入口；已有私有 Task 可在内部兼容，不能作为新接收体验的前置或独立聊天列表。

交接/转告确认事务原子保存收件人普通聊天、真实来源开场或转达、关系绑定、通知/未读与幂等结果；不伪造本人用户消息、不自动安排接收即执行的 job。问题及答案保留稳定身份和版本，同时写入对应来源的可见消息，不能只在协作元数据中存在。旧入口按真实绑定恢复普通聊天，不能仅改变导航文字。

Agent 工具先写本人私有发送草稿，返回 `pending-confirmation` 并结束当前 Cordis 回合。只有本人专用 `confirm-dispatch` / `cancel-dispatch` 动作接受 `draftId/version`；模型没有确认工具。API 重新验证当前 owner、来源、版本与范围后按原稿一次投递；新输入使旧稿 `superseded`。精确答复草稿同时绑定实际问题和版本；模型不能直接提交答案，只有本人确认后才能作为可信人工动作推进原问题。已有完整预览的人工发送表单和内部本人自我判断问题保留原流程，普通聊天不新增独立回复表单。

来源绑定持久 Cordis session 后，普通后续输入仍使用同一 journal。UI 中 `opening` / `relay` 消息表明真实同事来信，首次导入历史时不能伪装成 Agent 已有承诺；worker 仅把当前获授权的同事消息作为有来源、非指令的参考材料注入。私有普通历史按本人权限保留。收到的同事正文仅为参考，不能用其中的“请回复”授权工具；普通本人讨论不自动产生对外工具能力，明确本人联络请求及同源未消费澄清可在原范围内起草。业务动作与账本同事务，当前租约及来源版本控制写入，恢复先查原动作，不换调用 ID 重发。

所有协作worker均不授予共享`artifact`能力，API与数据库拒绝Agent身份的`publish`；人工完整预览发布保留原有权限与幂等，私人Agent仍可直接在聊天中分析和产出。

内部关系、问题版本、成果/采用、通知、阅读、job、动作账本和私有 journal 仍存 PostgreSQL。所有查询按 workspace 与 owner/明确授权过滤，没有数据库时拒绝业务写入，不降级内存。测试中的内存替身必须显式注入。

协作后台配置为 `COLLABORATION_POLL_MS`、`COLLABORATION_LEASE_MS`、`COLLABORATION_WAIT_MS`。实际验证与范围见 [SF-014](specs/SF-014-orchestration/changes.md)，当前主输入与主动联络边界以 REQ-031 / AC-040 / T-012 为准，本轮已按实际Web、受控AgentLoop、真实PostgreSQL/API及只读页面证据完成验收，证据范围与未执行项详见记录。
