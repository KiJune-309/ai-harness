## 背景与目标

SF-019 已独立验收，本项是用户要求的第六项看板。项目已有安全责任关系和待处理，但负责人仍须在关系列表中逐项找执行失败、等待自己处理或尚未开始的工作。看板应按实际工作状态聚合，帮助判断“现在先处理哪项”，而不重复画责任树。

本项在共享项目详情提供“概览 / 看板”切换，展示完整获授权工作及真实等待，支持搜索、负责人及待我处理筛选，并准确进入本人的原聊天或既有失败修复入口。看板只读派生，不创建新状态主记录，不把一次回答、没有等待或 `ready` 说成工作完成。

## 范围

### 范围内

- 共享项目详情的看板入口、稳定视图地址、六列状态卡片、真实总数与筛选、分批显示和刷新。
- 基于既有节点、合法 pending 和精确来源元数据派生 `sourceAvailable`、`started`，不返回聊天正文。
- 本人精确继续/历史查看/失败修复链接，其他成员安全只读。
- 当前Project/Workspace授权、故障/失权、历史异常及实际桌面/390px验收。

### 范围外

- 拖卡改业务状态、重排卡片、手工完成/恢复、批量操作、自定义列或审批状态机。
- 新增任务、模型执行、催办、联络草稿、自动发送、重新授权或恢复旧节点。
- 跨项目总看板、私人项目的个人Task看板；私人项目仍保留现有四状态任务管理，不混入共享节点看板。
- 普通聊天里的看板/项目/上下游面板、问题或答案全文、目标/上下文、Skills/模型配置公开。
- 真实共享文件、设备在线状态及交付物完成率；已有资料/成果保持原项目共享内容区。

## 入口、布局与筛选

- 在 `/projects/[id]` 的共享项目标题/操作区下、“项目成员”之前，增加“概览 / 看板”视图切换；默认概览保留SF-017内容，看板不再重复渲染完整责任树。成员和共享内容仍在下方，不增加全局侧栏或移动底栏入口。
- 看板地址为 `/projects/[id]?view=board`，可刷新/直接打开；其他值回概览。已有显式 `node/event` 深链继续按原授权工作入口处理，不被 `view` 劫持。进入他人/失权项目仍不得因URL显示内容。
- 看板标题下显示“当前获授权项目进度 · 全部 N 项工作”，以及“当前匹配 M 项”；不将等待请求数当工作卡数，不展示完成率。
- 工具区包含搜索（工作名称、负责人或短编号）、负责人选择（全部或真实负责人ID，自己标“我”）、“仅看待我处理”勾选、“清除筛选”和“刷新看板”。负责人以姓名+短编号区分，同名不同人不合并；历史负责人仍可筛选并标历史身份。
- 筛选在完整已读集合上做，组合条件取交集。“仅看待我处理”表示该工作是至少一项当前合法pending的实际目标且目标负责人是本人，不依据 `waiting-owner` 字样猜测。每工作只一张卡，同人多工作仍分别保留。
- 每列标题显示“匹配 x 项 / 全部 y 项”；无筛选时可只显示 y。整个项目没工作显示开始工作入口，无匹配显示清除筛选，个别列为空显示该列暂无匹配；不能拿加载/失败冒充空列。
- 同项目切换概览/看板保留本地筛选；换项目、账户或Workspace清空筛选及旧数据。重载/新打开看板默认全部，不把筛选保存成业务记录。
- 桌面按可用宽度多列排列，列内使用现有Card/Badge/Button；窄屏按列纵向排布，390px全部六组和操作均无需页面横向滚动。列名/计数、长标题/姓名和等待说明可换行，不依赖颜色传达状态。
- 每列默认显示最多20张匹配卡，提供“再显示20项（剩余N项）”，全部记录最终可达；过滤、总数和列计数始终基于完整集合，不能先截断再过滤。改变筛选重置每列显示额度，不悄悄丢掉第21项。

## 真实状态映射

每节点按下表自上而下首次匹配，恰好归一列。这里只派生展示状态，不能写回原node.status。

| 优先级 | 持久/安全事实                                                                                     | 看板列及卡片说明                                                                                                               |
| ------ | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 1      | `authorized=false`，或原状态cancelled/completed，或精确旧Task来源真实completed（不覆盖撤权/取消） | **已结束**。授权失效主标“授权已撤销”；其余分别“已取消”“历史已完成”。同时存在其他终态可保留次要Badge，但绝不把撤权/取消算完成。 |
| 2      | 非终态但精确source不存在/种类不符，或started未知，或历史awaiting-activation                       | **需要检查**。分别标“工作来源暂不可用”“开始状态暂不可确认”或“等待本人打开（历史记录）”。不推断为未开始，不新建激活入口。       |
| 3      | 原状态failed且来源可确认                                                                          | **需要检查**，标“执行失败”，不能当完成或自动恢复。                                                                             |
| 4      | 原状态running                                                                                     | **执行中**。若同时有合法等待，卡片继续显示全部等待，不因分列把它们隐藏。                                                       |
| 5      | 该节点是至少一项当前合法pending的请求方                                                           | **等待协作**，逐项显示实际处理对象和等待方向；含本人判断，不能只显示一个对象。                                                 |
| 6      | 来源存在且started=false                                                                           | **未开始**，指尚无该来源的持久本人输入；模板opening或收到relay不算本人开始。                                                   |
| 7      | 来源存在且started=true，其余可继续工作                                                            | **可继续**。一次回复结束仍在此类，不是完成；若原generic等待状态但已无合法pending，可说明“当前无有效等待”。                     |

`started` 只由服务器针对node精确的 `workspaceId/ownerId/sourceId/sourceKind` 读取已持久 `role=user` 输入是否存在派生；新空聊天、只有assistant opening/relay、查看页面都为false。它不表示当前模型已运行成功，也不由前端按钮点击、显示名或工作标题推断。精确来源缺失/种类不符时为null，不能伪造false；旧Task来源同样按实际持久本人输入判断，本项不更改旧Task.started。

本期普通聊天节点没有新增人工“完成”动作。“历史已完成”只承认已有真实completed记录；等待回答、答复完成、模型生成结束或没有pending都不产生该终态。合法pending被答复、拒绝、取消、到期或关联撤权后，下一次成功读取自然退出等待，按上述其他真实事实归列。

既有精确Task来源通过真实Task状态API保存为completed，也属于真实历史完成：可在数据库元数据查询中只读取该布尔，对非撤权、非取消节点将公开进度只读投影为completed、canContinue=false，并排除其作为待处理端点；不写回aggregate或修改原问题。本人通过原API恢复Task后，仅撤除这层来源完成的展示覆盖，再结合原node及当前授权判定；不能清除原node自己的终态、revocation/cancel fence或恢复旧grant。`started`仍只认持久本人user输入，绝不与旧Task.started做OR。

## 卡片与下一步

- 每卡仅展示公开工作名称、节点短编号、实际负责人姓名/短编号、真实状态、更新时间，以及可见上游名称/负责人；无效上游显示“原上游当前不可用”，不猜测隐藏内容。模板来源可保留原安全编号/版本，不公开模板全文。
- 显示该工作关联的合法等待：对外等待写“等待李四补充信息/处理协作请求”，指向本人的写“某工作正在等待此工作处理”，同节点问题写“等待本人判断”。按真实请求/目标节点和kind判定，完整问题/答案正文不进入看板。
- 同时有多个入站/出站请求时，卡上显示请求数和方向；默认显示3项，提供“展开其余N项”，全部可读。请求数与卡数分别说明，自己发给自己的单问题不能重复计两次。
- 每列先排实际待本人处理的卡；这些卡按最早待处理时间从旧到新，其余按工作更新时间倒序，最后以节点ID升序稳定排序。排序仅本地展示，不改责任关系或保存业务顺序。
- 本人且canContinue时“继续我的聊天”进入精确ownHref；自己的已结束且有合法历史链接时“查看我的聊天”，不能表示恢复执行。其他人的卡片只读，即使查看者是项目/团队owner也不提供他人来源链接。
- 本人的真实failed工作可提供“查看失败与修复”，进入原 `/projects/[id]?node=<该节点>` 受授权修复页面；看板点击只导航，不直接发retry、切Agent、请求模型或取消工作。缺失source/awaiting-activation卡没有本期新恢复/激活动作，说明可查看原已有入口或刷新确认，不伪造可继续。
- 若来源历史确实可读但节点已撤权，只保留原授权允许的本人历史查看；原服务拒绝读时显示安全失败，不自行重建聊天或回落他人来源。

## 数据与授权契约

- 复用SF-017安全progress，扩展每节点 `sourceAvailable:boolean` 和 `started:boolean|null`；前者表示精确来源行存在且kind正确，后者按上述真实输入判定。`authorized`继续表示节点/成员授权，`canContinue`继续表示本人当前可执行，两者都不能替代source存在性。
- 看板只消费白名单元数据、当前合法waits及本人ownHref；源消息只在数据库内用于布尔判定，不返回正文、user requestId、他人source ID、goal/context、私有Skill或模型字段。不通过读取他人完整chat/Task快照来计算started。
- 同一次完整读取的数据同时决定分列、总数、筛选与等待数；现有progress完整集合不新增隐式服务端截断。若未来改分页必须显式表达完整性并改验收，不能默默拿第一页当全部。
- 仅读取和筛选不创建board表/状态、Task、消息、job、通知、联络请求或模型调用，不访问任何个人模型凭据。个人浏览筛选不是业务主记录。
- 沿用自动刷新（可见时沿原3秒读取、请求不重叠、隐藏暂停）及手动刷新。成功结果展示最后确认读取时间；服务故障显示“刷新失败，当前仅上次成功读取的数据”并可重试，不以旧图冒称已更新。401/403/404、身份/Workspace切换清除旧看板和私有链接。
