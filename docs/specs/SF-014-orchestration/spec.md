## 背景与问题

用户希望同事各自与Agent推进工作，Agent把上下文、问题和成果沿真实责任关系接起来，避免用户复制、转述或重新解释背景，人保留业务判断。前版把核心缩成“Agent代发站内私信”理解偏窄：站内消息是协作载体，核心是同一事项中的多人上下游工作。

2026-10-19用户指出当前界面增加了过多任务/项目/上下游内容，而且来信未出现在普通Agent聊天中。用户明确确认接收内容“直接作为普通 Agent 聊天”。REQ-030/AC-039因此覆盖历史要求以Project/Task为主路径的界面和新交接存储方式：普通聊天列表直接收到真实来信，打开即正常Agent聊天；内部关系与旧Task兼容保留，不要求用户操作协作面板。发送前本人确认仍按REQ-029执行。

2026-10-19用户进一步要求删除额外回复区，并明确主输入是与自己的Agent理解需求和安排执行，不是自动回复同事。REQ-031/AC-040覆盖历史轻量精确回复表单和默认外发语义：只有本人主动要求联系、向上游补信息或回传，Agent才在该范围整理草稿并由本人确认；收到正文的请求不作为本人授权。共享成果也不能成为绕过此边界的路径：所有worker移除Agent artifact能力，API/数据库拒绝Agent直接publish；私人分析与产出留在本人聊天，保留既有完整预览后的人工发布。

文章及官方文档的产品/工程示例是：前线先补齐场景，产品收到上下文并可回问前线；问题到达前线原对话，回复返回对应节点继续，之后再交工程。用户已明确确认采用这个协作模型。本文据此修正原有消息需求，不把简单通知一律变成项目，也不要求每次使用“等回复”的固定口令。

现有代码的Project是个人任务归组，Task/Agent及模型按workspace/user隔离；共享响应不能直接复用含私有prompt/推理的完整PersonalTask。当前临时模型执行/内存互斥还不能可靠承担多人后台接力，需要在现模块内补齐持久协作关系和恢复。

## 目标

- @同事确认发送后，对方在普通聊天列表直接收到Agent开场和实际正文，打开即在自己的正常Agent聊天继续工作，无需接手任务或操作项目/上下游面板。
- Agent能先补齐缺失信息，下游仍可向上游追问；问题回原对话，回答自动归回提问节点并继续一次。
- 各人保留真实身份、私有Agent/模型和工作上下文，项目只共享被授权的工作材料、状态与成果。
- 站内必收、离线可回、刷新/重启不丢，失败/取消/撤销不重复或越权执行，人作最终判断。

## 范围

### 范围内

- 同workspace真实成员与人员提及，简单转告及协作委派意图区分，保留原文件/Skill和命令。
- 普通私有ChatConversation接收交接与转告，内部保留明确来源关系、版本化文本成果/上下文及授权引用。
- 原普通聊天内交接、Agent补问/回问、人回复/判断和按工作依赖续接；通知/未读为辅助入口，既有Task入口仅兼容。
- PostgreSQL持久记录/幂等/队列/恢复，个人模型隔离，现有项目/任务界面的渐进扩展。

### 范围外

- MacBook、服务器、浏览器节点的注册/路由/远程执行；飞书、微信及其他外部通讯适配仍后置。
- 完整组织/SSO、跨workspace协作、任意DAG/可视化SOP设计器；现有个人模板本轮保持，不声称已变为多人流程模板。
- 支付/财务规则/合同等特定业务审批引擎，或用Agent虚构同事替代真实人承担责任。
- 全量私聊/模型秘密共享、永久每人唯一Agent、自动使用未获本人授权的模型；新共享文件编辑系统或聊天RAG/向量权限扩展。

## 用户场景

1. 产品在原对话整理方案，说“@张三，请评估这个方案”。Agent先展示收件人和完整正文，产品确认后张三在普通聊天列表直接收到自己的Agent对话，开场显示真实产品同事、方案与问题；张三在普通输入框继续，不出现接手、任务、项目或上下游面板。
2. 工程缺少使用规模，对Agent说“帮我问发起人”。Agent整理回问草稿，工程本人确认后发送；问题作为可见消息出现在产品原聊天，产品先在正常输入框与自己的Agent分析、讨论；主动要求把补充信息回传后，Agent整理精确答复草稿，由产品本人确认再发。真实答案回到工程同一普通聊天并续接，最终可行性仍由工程负责人判断。
3. 前线最初只说“性能差”，Agent先追问场景/指标，再给产品；产品仍可追问，之后工程沿同一事项拿到成果，不拉用户作中转。
4. “@张三，把会议改到三点告诉他”生成轻量转告草稿，确认后正文也进入张三的普通Agent聊天，不强建Project或等待对方回复。收件人离线登录后可读回，接收和读回无需模型在线。
5. 任一成员关闭页面/服务重启可恢复；修订、取消或撤销后的旧回复不复活工作，私有Task不转移给项目创建者。

## 概念与状态约束

- **协作Project：**同一事项的稳定身份，聚合真实参与者、责任节点、共享材料和进度；与旧个人归组的自动共享语义分开。
- **本人聊天：**新接收内容保存在真实负责人自己的普通ChatConversation，使用正常列表、读取和聊天入口。旧责任Task仅内部兼容，不作为收到消息或开始聊天的门槛；他人不能读取完整私有对话。
- **协作事件：**有来源/目标节点和版本的交接、问题、答复、成果或判断；回问不等于新增反向执行依赖。
- **普通消息：**授权正文的轻量转告；成功发送不等于已读/同意，也不自动建立所有协作依赖。
- **发送草稿：**仅来源真实负责人可见的收件人、完整正文与共享范围，绑定稳定来源、动作槽和草稿版本。`pending`仅等待本人确认，`sent`才代表投递，`cancelled`/`superseded`不可再次发送；草稿不创建收件人通知、问题或私有Task。
- **状态：**四类任务工作状态继续由既有规则维护，另行记录节点等待/执行状态和问题版本；各节点独立推进，人的决定不能被模型猜作已完成。

## 非功能约束

- 维持AGENTS包边界、PostgreSQL主记录、真实身份授权及个人模型秘密隔离；API先授权再给core可信节点上下文，core不依赖NestJS并由Cordis推进。
- 普通私有Task与共享Project投影分离，成员不能冒用项目创建者scope，source原文/成果授权不等于开放全部私聊；协作输入不提升为系统指令。
- 自然语言联络意图由Agent系统策略与受限工具提示约束，受控provider验证正常讨论与主动联络路径，不宣称可对任何恶意模型的语义判断作强证明。服务端强制能力槽、来源、收件人、问题版本和当前权限，真实投递必须由本人专用draftId/version确认动作完成；即使合法槽产生草稿也不能自动发送。
- 持久仲裁覆盖用户发送/状态变更和后台续跑；模型网络请求在事务外，当前版本/租约才可结算，不以进程Map当业务互斥主记录。
- 搜索、消息/成果、分页、并发、步骤/等待期限及重试有限，等待不模型空转；错误保输入，不能假成功。
- 原组件/私有Portal与账户故障边界保持；函数多行JSDoc/TSDoc、测试同级且不进产物，工程格式/lint/类型/构建及真实PG证据完整记录。
