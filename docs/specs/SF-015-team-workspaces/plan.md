## 技术方案与理由

沿现有 contracts → db → API → Web 分层增量实现。保留默认部署空间的全部历史归属与模型加密绑定，显式团队使用独立成员表，不把组队等同于共享私有内容。用户已授权产品经理/实施/测试轮转，本计划沿该授权进入实现。

## 模块、接口与数据流

- contracts/workspaces：严格输入/公开响应；不包含会话、凭据或数据库对象。
- db/workspaces：复用现有连接池，保存团队、成员、稳定收件人邀请及会话活动范围；事务串行创建/接受/撤销/移除。
- API WorkspaceService/Controller：真实会话后处理 /account/workspaces；ChatGuard 解析持久活动空间并校验浏览器预期范围；AccountService 全局资料与空间内个人模型权限分别验证。
- Web：侧栏切换器、/workspaces、五类请求封装和三类BFF；X-Harness-Context 只用于拒绝过时页面，不作为授权来源；409配公开上下文变化标识。
- 协作db：有效成员目录、真实投递及租约内复验；退出使旧后台写入和草稿失效，并取消该成员的资料/向量待处理租约；对应worker只领取有效团队成员任务。保持原本人确认及私有 journal 边界。

## 数据、兼容与迁移影响

新增表使用 additive 初始化，保留原 workspaceId/userId 与加密AAD。默认空间无新拥有者。新会话从历史空间开始；活动空间只在其已持久会话上选择。邀请用邮箱定位后绑定稳定账户ID，改邮箱不转移。无需新增依赖或公开秘密配置；测试使用隔离 PostgreSQL schema。

## 风险与缓解

| 风险                     | 影响                   | 缓解                                                   |
| ------------------------ | ---------------------- | ------------------------------------------------------ |
| 旧标签页迟到请求         | 写入错误空间           | 请求绑定已验证范围，服务端比较，切换重载和跨标签页复验 |
| 邀请/撤销或移除/投递竞争 | 半成员或失权继续发送   | 团队事务锁、成员行锁、租约内复验、稳定动作ID           |
| 账户模型home假设         | 团队无法配置或秘密串用 | 授权改为成员校验，仍按user+workspace保存和加密         |
| 大量既有未提交工作       | 覆盖用户改动           | 文件分工与增量修改，不重置历史                         |
