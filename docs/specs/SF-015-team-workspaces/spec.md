## 当前修订与历史基线

2026-10-20 用户明确修订 `/workspaces`：收到邀请直接显示卡片，待处理卡以接受/拒绝两个图标操作；基本信息只读；创建成功保留当前空间和页面，由本人手动进入。共同创建 Dialog（含 Sidebar/移动 Sheet 入口）执行相同规则。

本次以 REQ-014–REQ-016、AC-017–AC-019 为最新界面验收要求，替代初版中编辑基本信息、创建后自动进入及邀请栏目样式的冲突描述。AC-001–AC-016 原文及已有 PASS 证据保留为初版历史，不据此宣称本次修订已完成；其余身份、权限、邀请/切换协议保持。

## 背景与问题

当前账户只有服务配置给定的 `workspaceId`。用户有真实账户和私有内容，协作目录却从相同部署空间的账户中选人，缺少“我属于哪些团队、当前在哪个团队、谁可以加入”的可见概念。用户要求依次建设 Workspace、Project、上下游、任务模板、Skills、看板；本规格只交付第一项，建立可创建、可邀请、可切换、可退出的真实团队边界，后续五项再分别设计和验收。

参考 Syncless 的组织方式：工作空间承载成员和协作资源，加入后才能在该空间被 @ 和参与协作。角色、邀请渠道和旧数据处理方式采用本项目现状下的明确产品选择，详见 [reference-notes.md](reference-notes.md)。

## 目标

- 用户能在现有侧栏看见当前工作空间，通过“创建工作空间 → 邀请同事 → 同事接受 → 切换进入”完成首次组队。
- 一个账户可以加入多个团队；当前空间中的业务列表、模型配置与协作对象只来自当前有效范围。
- 团队成员关系不授予他人私有聊天、任务、Agent、资料或个人模型密钥访问权。
- 原有聊天、协作、个人模型和资料不迁移、不丢失，原默认空间可继续访问。

## 范围

### 范围内

- 真实工作空间及成员持久记录、当前会话的活动工作空间、创建及只读展示团队基本信息。
- 拥有者/成员两级权限，站内邀请已注册邮箱、接受/拒绝、撤销与到期、成员名册、移除与主动退出。
- 统一工作空间切换器和 `/workspaces` 管理页面，桌面与移动端可操作。
- 现有业务授权和同事选择目录接入活动空间，保留现有私有与明确共享边界。
- 默认工作空间兼容旧数据，真实 PostgreSQL 持久化、重试与权限回归。

### 范围外

- 后续 Project 共享体验、上下游关系展示、拖拽任务模板、Skills 和看板。
- 邮件投递、未注册邮箱邀请、公开邀请码、邀请链接、SSO、域名自动加入、跨团队协作。
- 管理员等第三种角色、角色调整、拥有者转移、解散/删除工作空间、归档及组织部门。
- 工作空间间迁移或复制现有聊天、个人模型/密钥、Agent、项目、模板、资料和向量索引。
- 共享模型凭据、设备、外部 IM、计费配额或 Console API key。

## 界面位置与操作流程

### 固定入口

- 桌面侧栏和移动导航 Sheet 的 `orbit.` Logo 下方、“开始聊天”导航上方，增加一个全宽工作空间下拉触发器。显示当前名称和展开图标，长名截断且有完整可访问名称；不要放进个人账户菜单造成团队与账户混淆。
- 下拉菜单依次展示“我的工作空间”（当前项带选中标记，团队项带本人角色）、“工作空间管理”、 “创建工作空间”；有未处理邀请时，管理入口和触发器显示待处理数量。菜单列表在小屏内滚动。
- `/workspaces` 沿用现有主内容区的标题、说明、右侧主要按钮、卡片/表格和错误反馈。存在邀请时直接显示邀请卡片，无邀请不显示空栏目、标题或占位；随后列“我的工作空间”及所选空间的基本信息和成员。基本信息对所有角色均为纯文本只读，不提供编辑/保存；拥有者仍可邀请、撤销和移除成员，普通成员只读名册并可退出。
- 桌面不新增全局顶部栏；移动端在现有 Sheet 内提供相同入口，底部五项导航数量不增加。`/account` 继续管理全局用户名、邮箱、密码；其中模型配置说明为“当前工作空间的个人模型连接”。

### 创建与切换

1. 用户从切换器或管理页点击“创建工作空间”，默认 Dialog 输入名称、说明。
2. 保存成功只创建团队及本人拥有者关系，不切换本会话活动空间、不导航、不清空当前草稿，也不自动选中新空间详情。共同 Dialog 展示只读成功结果（新名称、说明及手动进入提示）和“完成”，刷新目录后新空间可被本人手动选择。侧栏和移动 Sheet 的创建入口同样适用。
3. 只有本人另行明确点击切换/进入空间时，才先由服务端确认活动空间，再完整进入 `/`；不把旧空间的对话选择、草稿、搜索、模型目录或详情地址带入新空间。
4. 切换前存在当前输入器未发送文本或未保存编辑时，用现有确认 Dialog 明确提示将丢弃本页未保存内容，默认保留当前页面；已保存内容不丢失。已开始的后台工作属于原空间，不因切换而迁移或重复启动。

### 邀请与加入

1. 拥有者在管理页点击“邀请成员”，输入一个已注册同事的邮箱；说明“发送站内邀请，对方接受后加入，不会发送邮件”。
2. 提交前确认规范化邮箱，提交成功只产生待处理邀请，不产生成员。未注册邮箱、自身、现有成员或已有有效待处理邀请给出就近反馈。
3. 收件人从切换器待处理提示进入管理页。邀请直接以卡片显示团队名称、说明、邀请人和有效期；待处理卡仅提供接受/拒绝两个图标按钮，保留清楚的可访问名称和 Tooltip。无邀请不展示“收到的邀请”空标题、空卡或“暂无邀请”占位。即使当前活动空间不同，也能看见只属于本账户的邀请。
4. 接受产生一个有效成员关系，保留当前空间，明确显示“已加入”并提供“进入工作空间”；拒绝不加入。邀请有效期七天，到期后不得接受，拥有者可在原邀请终结后重新邀请。
5. 拥有者在当前团队的“待处理邀请”列表看到规范化邮箱、时间和状态，可撤销仍待处理的邀请。普通成员看不到其他待加入者的邮箱或管理操作。

### 退出与移除

- 普通成员退出、拥有者移除成员均需确认，对话框写明团队与实际成员，说明“失去该空间访问权限；已有内容保留，不会转移给其他成员”。确认初始焦点位于取消。
- 拥有者不能退出、不能移除自己，不显示不可实现的转移/解散流程。普通成员不能移除他人或邀请。
- 退出当前团队后返回默认工作空间及 `/`。被移除者后续私有请求拒绝，在账户/工作空间复验时清除旧空间界面并回到默认工作空间；不得因仍持旧页面、会话或资源 ID 延续访问。重新邀请接受可恢复同一账户在原团队的原有私有内容，不自动重新执行旧动作。

## 角色与数据边界

| 能力                                            | 拥有者 | 成员   | 非成员/邀请待处理                |
| ----------------------------------------------- | ------ | ------ | -------------------------------- |
| 切换进入、读团队名称说明与有效成员名册          | 可以   | 可以   | 不可以；收件人仅可读自身邀请预览 |
| 当前团队内使用本人聊天、Agent、任务、模型、资料 | 可以   | 可以   | 不可以                           |
| 当前团队内被 @、作为新协作收件人                | 可以   | 可以   | 不可以                           |
| 邀请与撤销、看发出邀请                          | 可以   | 不可以 | 不可以                           |
| 管理页编辑团队名称/说明                         | 不提供 | 不提供 | 不提供                           |
| 移除普通成员                                    | 可以   | 不可以 | 不可以                           |
| 主动退出                                        | 不可以 | 可以   | 不适用                           |
| 读取他人私有内容/个人模型密钥                   | 不可以 | 不可以 | 不可以                           |

“默认工作空间”是服务配置原 `workspaceId` 的兼容显示名，不把全体历史账户指定给任意一个新拥有者。其原有数据归属与协作行为保留，界面说明“保留现有内容；需要明确团队边界时请创建工作空间”，不开放改名、邀请、移除、退出等团队管理操作。既有及新注册账户均保留默认空间入口；新注册账户不会自动加入任何显式团队。默认空间继续以真实用户隔离私有内容，不把历史内容展示为全员共享。

## 用户场景

1. 产品负责人创建“产品研发”，邀请已注册同事。对方主动接受并进入后，双方在该团队的同事目录能够选中彼此，团队外人员不出现。
2. 同一用户在“产品研发”和“客户交付”之间切换。每个空间拥有独立的本人内容和个人模型连接，旧默认空间中的历史仍能切回查看。
3. 普通成员查看团队成员并主动退出；拥有者也可移除该成员。该人失去团队访问和新消息投递资格，原私有历史不转给拥有者。
4. 接受邀请时网络丢响应，用户重试后只产生一个成员关系；已撤销或过期邀请不能被旧页面接受。

## 非功能约束

- API 验证真实会话和有效成员后给 core 可信 scope，Web 只依赖 contracts；不让 core 依赖 API/NestJS。全部数据库读写和检索继续带空间及权限过滤。
- 成员撤销与新投递/执行竞争必须有可复核的服务端仲裁，不能只依赖界面隐藏或进程内成员缓存。已开始的网络调用不能承诺撤回字节，但失权后不得据此开始新模型或对外投递。
- 邀请接受与撤销、成员退出与新投递、重复创建等竞争不留下半个成员/重复团队；数据库失败保持上次已确认显示。
- 不公开密码 verifier、会话 hash/原 token、加密字段或个人模型 key。邀请绑定稳定账户 ID，邮箱仅用于精确定位，不新增全站账户搜索。
- 函数遵循多行 JSDoc/TSDoc，测试置于模块同级 tests，遵循现有格式和提交约定。

## 依赖与假设

- **2026-10-20 用户反馈：**上述三个界面修改为直接实施授权，不新增审批；本次独立测试只将有真实证据的 AC-017–AC-019 标 PASS。

- 用户在 2026-10-20 明确授权“产品经理提出一项需求 → 主 agent 实现 → 测试 agent 测试”，按六项顺序推进。产品经理输出本项 Spec 即进入实施；不额外加入逐文档审批轮次。Plan/Tasks 由主 agent 补全，验收后才开始下一项。
- 当前无邮件服务，采用已注册邮箱的站内邀请；界面明确不会发送邮件。邀请身份以发出时稳定收件人账户为准。
- 默认空间是对部署既有范围的兼容命名，保留原成员识别/协作能力；严格团队隔离从用户显式创建并邀请的团队开始。
- 本期两级角色满足创建、使用与成员维护；拥有者必须保留，移交/解散另行规格，不用隐藏功能冒充可操作入口。
- 团队共享项目和流程设计留待第二至六项，不由本期成员关系自动开放私有内容。
