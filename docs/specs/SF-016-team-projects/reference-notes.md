# SF-016 参考与现状记录

## 官方参考

- [Project](https://docs.syncless.ai/zh-Hans/core-concepts/project/)，2026-10-20 完整读取：以项目承接相关工作、多人及共享材料；个人长期主题可以先独立使用，明确的协作事项再让其他人参与。参考也介绍模板、上下游和看板，本项不提前实现那些独立阶段。
- 官方页面没有规定本项目的角色、表单、成员加入协议、资料版本协议。本规格的统一卡片、两级项目身份、人工选择成员及项目级文本资料均为结合本系统的产品决定，不声称复刻参考产品页面。

## 仓库已确认事实

- SF-003 提供个人项目、本人任务归组和模板来源；项目说明原为管理信息，不自动进入模型。
- SF-014 最新约定要求普通聊天接收协作消息、只有本人输入才执行、Agent 起草发送必须由真实本人专用确认；不回退到旧节点接手面板。
- SF-015 已新增会话活动 Workspace、owner/member、真实站内邀请和撤权。项目成员必须进一步限制项目访问，不能以团队 owner 自动替代项目 owner。
- `apps/web/components/project-workspace.tsx` 新建目前只保存个人项目，列表分开渲染协作卡片/个人卡片，同 ID 个人记录会遮掉协作卡片；列表没有两类整体统一排序。
- `packages/db/src/collaboration.ts` 的 delegate 在首个协作事项产生时，同时写个人项目壳和同 ID 的共享状态；`apps/api/src/chat-service.ts` 的个人项目编辑只写壳，公共元信息可漂移。
- `apps/web/components/collaboration-workspace.tsx` 的共享详情主要为责任条目/上下游/成果；节点本人路径会进入普通聊天，原人工发布成果表单因依赖节点页而不容易找到。
- 现有 `CollaborationArtifact` 要求 `nodeId`。新项目资料不应为了满足这个结构伪造责任工作，需在同一持久协作边界扩展项目级资料，既有 artifact 保留。

## 本项采用与保留

- 采用：单一项目入口、可见范围、共享元信息和成员、人工共享正文、稳定地址与权限。
- 保留：所有私人历史、原任务归组、真实普通聊天、已有协作事项和成果版本、人工发送确认。
- 留待后续：上下游体验第三项，带处理人拖拽模板第四项，Skills 第五项，看板第六项。项目文件/自动 RAG 另行需求，不以本期文字共享冒充。
