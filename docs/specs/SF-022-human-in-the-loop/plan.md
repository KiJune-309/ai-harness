## 技术方案与理由

用户收到完整需求稿后明确“开始执行”，本轮据此确认规格并获得实施授权，不再重复询问已授权范围的执行许可；不声称用户逐字审阅了本轮随后编写的计划。

复用 PostgreSQL collaboration source/job/journal 作为持久执行通道，普通聊天进入既有 enqueue 但不创建节点或共享项目。Core 注册 ask-human 与可信工具策略，持久请求后结束轮次；决定后原 job 重新 queued，按原 journal 的 callId 恢复，不能让模型重新拟操作。已完成的前置工具不重复。

工具结果占位在恢复时通过 Cordis surface 的追加替换记录补入真实答案/结果；原历史保留。API 绑定当前租约的 HumanLoopPort；等待请求保存不提前释放租约，journal flush 后由 worker settle(waiting) 释放。只读自动执行，生产发送保留原草稿确认；隔离有影响工具仅通过服务端显式依赖注入验证，不加入生产目录。

## 模块、接口与数据流

- contracts 新增 HumanRequest/HumanResponse/HumanDecision，ChatConversation.humanRequests 可选投影，消息可携精确 humanResponse。
- db 新增请求、决定及效果记录，绑定本人/空间/source/job/session/call 和权限代次。决定与真实答案、旧草稿替代和原 job 恢复同事务。
- core 在持久 runtime 增加 HumanLoopPort、主动提问、实际工具执行拦截及原调用恢复。同批未完成调用保存并按原顺序处理，遇新阻塞停下。
- API messages 接收底部回答；POST /chat/conversations/:id/human-requests/:requestId/decisions 接收本人批准/拒绝/取消；worker 注入当前租约端口。
- Web 问题/操作预览位于正文后，仍只有底部输入器；稳定 actionId/version 决策，失败保稿、丢响应核验。后台执行沿用持久会话轮询。

## 数据、兼容与迁移影响

- PostgreSQL 启动初始化新表及索引，不重写旧消息、不降级内存。
- 新公共字段可选，显式测试 fake 保留原运行入口；生产使用真实持久通道。
- 与 SF-021 普通聊天/文件夹及资料接口集成，不复活已删除旧项目路径，保留其他任务现有改动。

## 风险与缓解

| 风险                        | 影响             | 缓解方式                                        |
| --------------------------- | ---------------- | ----------------------------------------------- |
| 请求已保存但 journal 未完成 | 恢复缺调用       | wait 不释放租约，flush 后 worker settle         |
| 决定与恢复安排分离          | 丢恢复或重复执行 | 同事务动作账本和原 job queued                   |
| 模型重拟批准内容            | 越过精确审批     | 按 callId 冻结和恢复，参数变化新请求            |
| 外部效果后崩溃              | 重复副作用       | executing 记录及幂等核验，无证据则 unknown 停止 |
| 后台与普通写入竞争          | 覆盖/失权执行    | 共享 source 版本、租约和当前授权                |

### 2026-10-22 — 实际实现收敛

- 请求调用身份采用 `journal:<原调用位置>:<nativeCallId>`，恢复时同时校验原 job、turn/step、调用位置及参数；不信任模型复用的 native ID 或资料正文中的等待 JSON。
- 有影响工具可显式提供只读 `lookupResult`，按原身份核验已发生结果；没有可靠证据时转 unknown，不重做正文。
- 普通聊天的来源投影取得精确 source 锁后重读消息，再读取请求与活动状态，避免成功状态配旧回复的混合快照；未增加全 Workspace 写锁。
- 恢复阶段使用独立、稳定的 assistant 消息身份，成功或失败均保留首次分析及先前阶段；Web 继续只有一个底部输入器。
