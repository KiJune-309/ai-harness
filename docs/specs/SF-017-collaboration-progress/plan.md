## 技术方案与理由

复用现有PostgreSQL协作aggregate、问题和动作账本。新增独立安全进度投影，不把完整节点/问题当项目公开数据。人工开始命令在一个事务创建本人根节点、空普通聊天及bound来源，保持原首次输入/发送确认流程。

## 模块、接口与数据流

- contracts/collaboration增加project-start人工命令及进度白名单，旧响应兼容。
- db/collaboration在Workspace→成员→aggregate→source锁序下复验project成员及revision，持久幂等创建；关系/待处理从原node/question派生，终结与永久撤权过滤。
- API准备非秘密Agent快照和本人空聊天，不解析provider连接、解密key或执行模型；公开进度按会话范围授权。现有delegate从绑定source查找同Project及上游。
- Web team-project在原概览内组织我的工作、待处理与纵向责任链；有限遍历处理多根/孤立引用/环，不引入图编辑器。本人开始表单失败保稿、冲突明确重读；正常chat不增加面板。
- AGENTS及UI规范同步进度派生与私人目标边界。

## 数据、兼容与迁移影响

沿用原JSON aggregate与普通聊天/来源表，不引入新的关系主记录。新节点的目标来自本人明确输入，项目description/notes不复制到上下文；旧节点、深链、普通聊天和个人模板保持。已撤权节点永久不可恢复执行。

## 风险与缓解

| 风险                            | 缓解                                                         |
| ------------------------------- | ------------------------------------------------------------ |
| 进度API泄露正文或private source | 字段白名单、本人链接单独授权、秘密标记负例                   |
| waiting-owner误导目标或丢多等待 | 从每条真实pending目标推导，独立列方向/人/时间                |
| 开始动作创建半记录或重试重复    | 同事务/持久requestId/当前项目revision，真实故障与并发验证    |
| 旧关系环或深链溢出              | 有限遍历及异常组，移动端固定宽度纵向布局                     |
| 创建提前调用模型/扩大授权       | human-only、非秘密route快照、零jobs/messages，首次输入才执行 |
